1. INTRODUCCIÓN

1.1. Generalidades

QrPass es un prototipo funcional que digitaliza el proceso de abordaje y recaudo en transporte público mediante códigos QR. Combina una API REST desarrollada con FastAPI, una interfaz web tipo PWA para pasajero y conductor, y un esquema de datos relacional basado en SQLAlchemy con SQLite para entorno de demostración.

1.2. Justificación

El recaudo manual presenta dificultades en el control, trazabilidad y agilidad del proceso. QrPass registra cada abordaje como un Pago + Viaje, controla el turno del conductor, habilita el uso de QR firmado y mantiene la integridad entre saldo, recaudo y transbordos.

1.3. Objetivo General

2. DESCRIPCIÓN GENERAL DEL SISTEMA

2.1. Propósito

Proveer una plataforma de demostración para el cobro de pasajes con distintos medios: efectivo, tarjeta y saldo mediante escaneo de QR del bus. Todo con control por roles, idempotencia, validación de turnos y trazabilidad financiera.

2.2. Alcance

  • Autenticación y registro de pasajero
  • Gestión de billetera (recargas)
  • Cobro de pasaje (efectivo, tarjeta y QR del bus con saldo)
  • Gestión de turno del conductor (iniciar, generar QR, cerrar)
  • Historial de pagos y viajes
  • Transbordos (ventana de 20 minutos)
  • Consulta de rutas, tarifas vigentes y estado del servicio

2.3. Actores

Actor Descripción
Pasajero Usuario con rol PASSENGER. Puede recargar, pagar, consultar historial y aplicar transbordos.
Conductor Usuario con rol DRIVER (puede tener también PASSENGER). Gestiona su turno y genera QR.
Sistema (API) Encargado de validar reglas, firmas, idempotencia e integridad de datos.
Administrador/Demo Consultas de métricas y utilidades de demostración.

2.4. Restricciones

  • Entorno demo: no se procesan pagos reales
  • SQLite para entorno de demostración (qrpass.db o :memory: para pruebas)
  • Autenticación por token Bearer firmado con QR_PASS_AUTH_SECRET
  • Claves foráneas activas en SQLite
  • Validación con Pydantic v2

ID Regla Descripción

RN-09 Transbordo ventana 20 min Debe aplicarse dentro de los 20 minutos desde el viaje origen.
RN-10 Saldo suficiente para QR Se valida antes de descontar y crear viaje/pago.

4. ANÁLISIS Y DISEÑO

4.1. Análisis del Dominio

El dominio se centra en: Usuario, Roles, Conductor, Vehículo, Empresa, Ruta, Tarifa, Turno, Código QR, Pago, Viaje, Transbordo, Tarjeta.

Las entidades financieras mantienen trazabilidad: Pago guarda saldo_anterior, saldo_posterior, monto, medio, tipo_movimiento e idempotency_key. Viaje vincula el cobro con ruta, tarifa y turno cuando aplica.

4.2. Diseño Orientado a Casos de Uso

Se identificaron casos de uso principales documentados en documentacion/casos_de_uso/. Cada uno mapea a endpoint, servicio y modelos ORM.

4.3. Patrón de Diseño

Arquitectura MVC adaptado a FastAPI:

  • Model (M): app/models/ - Entidades SQLAlchemy, relaciones, restricciones.
  • View/Representation (V): app/dtos/ - Esquemas Pydantic para entrada/salida.
  • Controller (C): app/controllers/ - Routers FastAPI, validación, inyección de dependencias.
  • Service Layer: app/services.py - Lógica de negocio, reglas, transacciones.

4.4. Principios Aplicados

  • Separación de responsabilidades (SRP)
  • Inversión de dependencias vía Depends()
  • Validaciones con Pydantic y excepciones de dominio (ErrorDominio)
  • Idempotencia en operaciones financieras
  • Transaccionalidad para mantener consistencia
  • Trazabilidad con timestamps y saldos históricos

5. ARQUITECTURA DEL SISTEMA

5.1. Arquitectura General

QrPass sigue una arquitectura cliente-servidor con separación entre frontend y backend.

[Frontend PWA (HTML/CSS/JS)] --HTTP/JSON--> [FastAPI API REST /api/v1]
                                                |-- Controllers
                                                |-- Services
                                                |-- Models (ORM SQLAlchemy)
                                                |-- SQLite

5.2. Estructura del Backend

backend/app/
├── main.py
├── database.py
├── auth.py
├── passwords.py
├── services.py
├── controllers/
├── dtos/
└── models/

5.3. Flujo de Petición

  1. Cliente envía petición HTTP a /api/v1/...
  2. FastAPI enruta al controlador
  3. Dependencias inyectan Session y UsuarioAutenticado si aplica
  4. DTO valida payload/params
  5. Controlador delega a services.py
  6. Servicio aplica reglas, consulta/actualiza ORM
  7. Transacción commit/rollback
  8. Respuesta serializada con response_model
  9. FastAPI retorna JSON

5.4. Manejo de Errores

  • Validación Pydantic → 422 Unprocessable Entity
  • Errores de negocio (ErrorDominio) → manejador global en main.py retorna JSONResponse con status_code y detail. Para 401 añade WWW-Authenticate: Bearer
  • Errores de autenticación/autorización → gestionados en app/auth.py
